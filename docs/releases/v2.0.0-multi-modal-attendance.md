### Modality 1: Biometric Face ID (Autonomous Dual-Gate Telematics)
- **Primary Use Case:** Zero-touch, high-throughput boarding & alighting on camera-equipped fleet buses. Eliminates student queues, lost physical cards, and phone battery failures.
- **Biometric Pipeline:**
  - Onboarding 3D oval reticle with multi-angle rotational liveness challenge.
  - Normalized 512-dimensional vector embedding extracted on-device via WebGL/Canvas (no raw facial photos stored in database, compliant with DPDP Act 2023 & GDPR).
- **Matching Engine:**
  - Supabase `pgvector` with HNSW cosine similarity index (`vector_cosine_ops`, `m=32, ef_construction=128`).
  - Stored procedure: `match_student_face(query_embedding, match_threshold, match_count, filter_route_id)`.
- **Driver Gate Console:**
  - Real-time video canvas simulator (`DriverGateCameraConsole.tsx`) with Gate In (Front Door) and Gate Out (Rear Aisle).
  - Live hardware GPS coordinates bound directly from driver telematics (`currentCoords` / `realDeviceGpsRef`).
- **Autonomous Security Intruder Shield:**
  - Unregistered commuters detected entering Gate In automatically trigger `CRITICAL` incidents in `bus_security_incidents`.
  - Dispatches immediate audio-visual siren to the Transport Manager Security Center (`/transport-manager/security`).

### Modality 2: Dynamic Rolling QR (HMAC-SHA256 Time-Variant Pass)
- **Primary Use Case:** Commuter self-presentation via smartphone screen when boarding conductor-assisted vehicles.
- **Cryptographic Security:**
  - Time-based rolling tokens refreshed every 15–30 seconds.
  - Signed with HMAC-SHA256 using an institutional secret key and millisecond timestamp epoch to prevent screenshot sharing or proxy boarding.
- **Components & Routes:**
  - Student Display: `/portal/qr/show` (`DynamicStudentQrPass.tsx`).
  - Validation Endpoints: `/api/boarding/rolling-token`, `/api/boarding/scan`.

### Modality 3: RFID IoT Smart Cards (Physical Contactless Tap)
- **Primary Use Case:** Seamless offline or hardware-based student boarding using contactless MIFARE / NFC cards and ESP32 IoT bus door readers.
- **Hardware Architecture:**
  - ESP32 microcontrollers with RC522 RFID reader modules paired to vehicle Wi-Fi/LTE hotspots.
  - Local card UID validation cache with asynchronous batch sync to cloud backend.
- **Management Hub:**
  - Transport Admin RFID Desk: `/transport-admin/rfid`, `/transport-admin/esp32`.
  - Card pairing, lost card deactivation, and terminal event inspection.

### Modality 4: Static Conductor / Seat QR (GPS Geofenced Self-Service)
- **Primary Use Case:** Zero-hardware commuter self-service boarding where students scan a static bus placard or seat QR code with their mobile device.
- **Geofence Security Check:**
  - Validates student device GPS coordinates against the real-time bus location.
  - Requires distance $\le 100\text{ meters}$ and route stop proximity to prevent remote check-ins.
- **Components & Endpoints:**
  - Printable Seat QR Sheets: `/transport-admin/buses/[busId]/seat-qrs`.
  - Verification API: `/api/students/board-self-service`.

## 3. Database Schema Reference

The following database tables support the four attendance modalities:

| Table Name | Primary Modality | Key Columns & Indexes |
| :--- | :--- | :--- |
| `student_face_profiles` | Modality 1 (Face ID) | `student_id (TEXT, FK)`, `face_embedding (vector(512))`, `HNSW cosine index` |
| `bus_gate_events` | Modality 1 (Face ID) | `bus_id`, `gate_type (GATE_IN/OUT)`, `is_authorized`, `latitude`, `longitude`, `stop_name` |
| `bus_security_incidents` | Modality 1 (Face ID) | `bus_id`, `incident_type`, `severity`, `status (ACTIVE/ACKNOWLEDGED/RESOLVED)` |
| `attendance_records` | Shared Core | `student_id`, `bus_id`, `date`, `method (BIOMETRIC_FACE_ID, QR_SCAN, RFID, MANUAL)` |
| `bus_reservations` | Shared Core | `student_id`, `trip_id`, `status (BOOKED, BOARDED, ALIGHTED, COMPLETED)` |
| `rfid_tags` / `students` | Modality 3 (RFID) | `rfid_card_id`, `last_tapped_at`, `status` |
